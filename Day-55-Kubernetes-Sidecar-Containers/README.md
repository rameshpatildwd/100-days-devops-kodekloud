# Day 55 – Kubernetes Sidecar Containers

## Task / Requirement
We have a web server container running the nginx image. The access and error logs generated by the web server are not critical enough to be placed on a persistent volume. However, Nautilus developers need access to the last 24 hours of logs so that they can trace issues and bugs. Therefore, we need to ship the access and error logs for the web server to a log-aggregation service. Following the separation of concerns principle, we implement the Sidecar pattern by deploying a second container that ships the error and access logs from nginx. Nginx does one thing, and it does it well—serving web pages. The second container also specializes in its task—shipping logs. Since containers are running on the same Pod, we can use a shared emptyDir volume to read and write logs.

**Requirement details:**
- Pod name: `webserver`
- Volume name: `shared-logs`
- Volume type: `emptyDir`
- Containers:
  - `nginx-container` using image `nginx:latest`
  - `sidecar-container` using image `ubuntu:latest`
- Shared mount path: `/var/log/nginx`
- Sidecar command: `"sh","-c","while true; do cat /var/log/nginx/access.log /var/log/nginx/error.log; sleep 30; done"`
- Kubernetes access: `kubectl` configured on jump host

---

## Steps Performed
- Created a Pod definition using the Sidecar pattern
- Defined an `emptyDir` volume to store Nginx logs
- Mounted the shared volume into both containers
- Deployed the Pod to the Kubernetes cluster
- Verified logs were accessible from the sidecar container

---

## Commands Used

```bash
# Create the pod with sidecar configuration
kubectl apply -f sidecar.yaml

# Verify pod status
kubectl get pods

# Describe the pod
kubectl describe pod webserver

# Check logs from sidecar container
kubectl exec webserver -c sidecar-container -- cat /var/log/nginx/error.log
```

---

## Expected Outcome
- Pod `webserver` is created successfully
- Both `nginx-container` and `sidecar-container` are in Running state
- Nginx writes access and error logs to `/var/log/nginx`
- Sidecar container can read log files from the shared volume
- Logs are continuously streamed every 30 seconds
- Application follows separation of concerns

---

## Key Learnings
- `Sidecar` containers extend functionality without modifying the main application
- Containers in the same Pod can share data using `emptyDir` volumes
- `emptyDir` is suitable for temporary data such as logs
- The `Sidecar` pattern is commonly used for logging, monitoring, and proxies
- Separation of concerns improves maintainability and observability
- Multiple containers in a Pod share the same network and storage
